# Диагностика Happy

[← README](../README.md) · [Установка](installation.md) · [Настройка](configuration.md)

## Логи сервиса

Для Docker:

```sh
docker compose ps
docker compose logs -f --tail=100 happy
```

Для Ubuntu/systemd:

```sh
sudo systemctl status happy
sudo journalctl -u happy -f
```

Открой логи перед повторной попыткой добавления или обновления подписки. Путь `/api/subscriptions` добавляет ссылку; `/api/subscriptions/{id}/refresh` загружает узлы у провайдера. Само добавление не делает запрос к провайдеру.

## 403 при добавлении: проверка Origin

```text
subscription.add received
api.origin rejected status=403 ... origin="https://vpn.example.org" expected_origin="http://vpn.example.org"
```

Это отказ Happy до обработки формы. Сравни `origin` и `expected_origin`: схема, домен и порт должны совпадать. Для HTTPS за reverse proxy задай публичный адрес без завершающего `/`:

```yaml
environment:
  HAPPY_PASSWORD_FILE: /run/secrets/admin_password
  HAPPY_ORIGIN: https://vpn.example.org
  HAPPY_SECURE_COOKIE: "true"
```

Пересоздай контейнер после изменения Compose. Backend не доверяет произвольным `X-Forwarded-*` заголовкам. Проверку Origin отключать не требуется.

Если запрос не появляется в логах Happy, проверь адрес, запущенную версию контейнера и логи reverse proxy: отказ мог произойти до приложения.

## Ошибка при обновлении: ответ провайдера

```text
subscription.fetch response ... status=403
subscription.fetch failed ... stage="response"
```

HTTP-статус в `subscription.fetch response` относится к ответу провайдера. Сам API Happy возвращает ошибку обновления как HTTP 400; это не тот же статус, что ответ внешнего сервера.

Диагностика включает хост, итоговый хост после перенаправления, длительность, систему и модель клиента, User-Agent, отпечаток HWID и признаки отказа:

| Поле | Значение |
|---|---|
| `hwid_max_devices_reached=true` | Провайдер сообщил о превышении лимита устройств |
| `hwid_not_supported=true` | Провайдер не принял поддержку HWID шлюзом |
| `hwid_active=true` при HTTP 404 | Провайдер отказал HWID шлюза |
| `redirected=true` | Итоговый URL отличается от исходного |

Happy отправляет `User-Agent: Happy/0.1`, `X-Hwid`, систему и модель шлюза. HWID постоянный и сохраняется с данными приложения; шлюз занимает собственное место в лимите устройств. При ограничении приложения или устройства проверь кабинет и условия провайдера.

При сетевой ошибке запись `subscription.fetch request_error` содержит тип ошибки, признаки таймаута и отмены. Полный URL подписки, тело ответа, исходный HWID и ключи узлов не выводятся.

## Провайдер ответил 200, но узлы не появились

Смотри `stage="parse"` и текст ошибки. Номер строки относится к исходному декодированному списку, включая комментарии и пустые строки.

- Неизвестные протоколы пропускаются. Запись `subscription.parse unsupported_skipped count=2` означает, что пропущены две ссылки.
- Hysteria2 пока не поддерживается; его [план реализации](hysteria2-plan.md) учитывает отдельный официальный клиент и проверку `pinSHA256`.
- Поврежденная ссылка поддерживаемого протокола, неизвестный транспорт или отказ провайдера по HWID останавливают импорт.
- Если поддерживаемых узлов не осталось, обновление завершается ошибкой.

При неудачном обновлении сохраняются последние корректные узлы и сведения о подписке. Полные ссылки, пароли и содержимое подписки не добавляй в публичные issue или логи.

## Панель доступна, но устройство не выходит в интернет

1. Укажи внешний адрес сервера в настройках и открой настроенный UDP-порт WireGuard; по умолчанию это 51820.
2. Проверь, что клиент включён, а его конфигурация актуальна после изменения адреса, порта или ключей.
3. Выбери узел и включи выход. Без выбранного узла клиентский трафик заблокирован.
4. Выполни «Проверить выход»: HTTPS-проверка проверяет прокси-маршрут, но не WireGuard-канал конкретного устройства и не UDP провайдера.
5. Проверь DNS отдельно. Настройка основного DNS и поведение при сбое описаны в [руководстве](configuration.md#dns-прокси).

«Пинг всех» измеряет время TCP-подключения к порту узла. Это не ICMP и не проверка авторизации у провайдера.
