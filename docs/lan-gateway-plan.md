# План: режим LAN-шлюза для Happy

Статус: идея для будущей реализации. Документ фиксирует требования; режим пока не реализован.

## Цель

Добавить к WireGuard режим приема трафика от устройств локальной сети. Пользователь указывает отдельный LAN-адрес Happy как default gateway на устройстве, после чего его интернет-трафик TCP/UDP проходит через выбранный сервер подписки. VPN-клиент на устройстве не нужен.

Пример адресов:

```text
Основной роутер:    192.168.1.1
Сервер с Happy:    192.168.1.10
Отдельный IP Happy: 192.168.1.20

Устройство → 192.168.1.20 → Xray → выбранный сервер подписки → Интернет
```

Адреса приведены только для иллюстрации. Адрес Happy должен быть свободным и исключенным из динамической выдачи DHCP либо зарезервированным.

## Обязательное требование: сохранить работу соседних сервисов

SSH, torrent и остальные приложения на том же сервере должны продолжать работать через существующую сеть независимо от состояния Happy.

- Не менять default gateway основного сетевого namespace сервера.
- Не перехватывать исходящие соединения соседних приложений.
- Не заменять и не очищать существующие правила firewall.
- Сохранить доступность сервисов на основном IP сервера.
- Запуск, остановка, сбой Happy и переключение узла подписки не должны нарушать сеть соседних сервисов.

## Предпочтительная архитектура

Выделить Happy отдельный network namespace с собственным IP в LAN, маршрутами и правилами перехвата. Системную подготовку сети выполнять отдельно от непривилегированной веб-панели.

Способ подключения namespace к LAN выбрать после изучения сети сервера: macvlan либо veth через Linux bridge. Bridge сам по себе не обеспечивает изоляцию; дополнительный IP на основном интерфейсе также не изолирует сетевой стек.

При выборе учесть ограничения macvlan для связи с хостом и поддержку нескольких MAC-адресов сетевым оборудованием. Перенос физического интерфейса в bridge может кратковременно прервать сеть, поэтому такой переход требует отдельного плана применения и отката.

Точный состав процессов внутри namespace определить при проектировании: Xray должен принимать трафик шлюза в изолированной сети; доступ панели, ее связь с ядром и существующий WireGuard должны быть явно предусмотрены.

## Прием и маршрутизация трафика

- Использовать прозрачный вход Xray с TPROXY, nftables и policy routing для TCP/UDP с сохранением исходного назначения.
- Ограничить прием доверенным LAN-интерфейсом и настроенными источниками.
- Отправлять трафик через единый выбранный выход подписки.
- Сохранить возможность использования WireGuard параллельно с LAN-шлюзом.
- При отсутствии действующей подписки, выбранного узла или работающего ядра блокировать интернет через шлюз; прямого обходного выхода быть не должно.
- Обеспечить доступ Xray к провайдеру через основной роутер без зацикливания перехвата.
- Явно определить доступ клиентов к LAN и сервисам хоста; существующую блокировку частных адресов для WireGuard не ослаблять автоматически.

## DNS и IPv6

Предусмотреть DNS через Happy. Если клиент использует DNS основного роутера в той же подсети, такие запросы могут обходить шлюз; одной смены default gateway недостаточно.

IPv6 должен иметь явную политику: поддерживаемый маршрут через Happy либо отключение на тестовых клиентах/сегменте. Смена только IPv4-шлюза не предотвращает прямой выход по IPv6. Полную блокировку обхода при сохранении альтернативных шлюзов на клиентах гарантировать нельзя.

## Интеграция

- NixOS: декларативные опции для режима, LAN-адреса, интерфейса подключения и разрешенных источников; отдельная подготовка namespace, маршрутов и firewall с корректным порядком запуска и остановки.
- Ubuntu: эквивалентная подготовка через systemd и системные сетевые настройки.
- Docker: отдельное проектирование LAN-подключения; обычного Docker bridge недостаточно для доступного устройствам LAN шлюза.
- UI: состояние режима и сетевых зависимостей, настройки и понятные ошибки.
- Мониторинг: учет трафика нового входа вместе с WireGuard без учета служебных проверок.

## Ограничения

Happy выступает прокси-шлюзом для поддерживаемого TCP/UDP-трафика, а не универсальным туннелем всех IP-протоколов. Передачу ICMP и обычного ping через подписку не обещать.

Клиенты должны иметь сетевую доступность до LAN-адреса Happy. Обмен между устройствами одной подсети обычно проходит напрямую и не попадает на default gateway. DHCP-сервер и автоматическая выдача шлюза в первоначальный объем не входят.

## Проверки перед выпуском

1. Устройство с gateway Happy выходит в интернет через выбранный узел; TCP, UDP и DNS проверяются отдельно.
2. WireGuard сохраняет работоспособность при включенном LAN-режиме.
3. SSH остается доступным на основном IP сервера при запуске, остановке, сбое ядра и переключении узлов.
4. Исходящие соединения соседних сервисов, включая torrent, сохраняют обычный маршрут; проверяются существующие и новые соединения.
5. При отказе Happy или подписки клиентский трафик не уходит напрямую, а сеть хоста продолжает работать.
6. Проверяются DNS и IPv6 на обход прокси в поддерживаемой конфигурации клиентов.
7. Перезагрузка и повторное применение NixOS-конфигурации не создают дублирующих правил; удаление режима не повреждает существующую сеть.
8. Доступ к панели и предусмотренным LAN-ресурсам соответствует выбранной политике.
